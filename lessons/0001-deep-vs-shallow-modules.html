Complexity Is the Enemy

Before patterns, before architecture diagrams — the one thing every design decision is secretly about. And the one judgment AI can't make for you.

You asked to start with the hardest strategic muscle: codebase design. Here's the reframe that makes it learnable. "Design" sounds like it's about diagrams, layers, and design patterns. It isn't. Underneath all of it is a single goal:

The whole game Good design is the ongoing fight to keep complexity from accumulating. Every other principle — modularity, abstraction, "clean code" — is a tactic in that fight. — the central thesis of John Ousterhout's A Philosophy of Software Design.

Why does this matter now, for you? Because AI has changed what's scarce. AI will happily generate a thousand lines that work. What it won't reliably do is tell you whether those thousand lines made your codebase easier or harder to change next month. That judgment — is this design adding or removing complexity? — is the strategic skill. It's what you'll be paid for when the typing is free.

Knowledge · What complexity actually is

Complexity isn't "lines of code" or "this is hard math." Ousterhout gives a precise, usable definition: complexity is anything about a system's structure that makes it hard to understand or modify. It shows up as three symptoms:

  • Change amplification — a simple change requires edits in many places.
  • Cognitive load — you must hold a lot in your head to make a change safely.
  • Unknown unknowns — it's not obvious what you need to change, or what your change will break. (Ousterhout calls this the worst one.)

And it comes from two root causes: dependencies (one piece can't be understood or changed in isolation) and obscurity (important information isn't obvious). Almost every design technique is an attempt to reduce one of these.

Knowledge · The sharpest tool — module depth

Think of any unit of code — a function, a class, a service — as having two parts:

Interface (what a caller must know to use it)   vs.   Implementation (the machinery inside)

The cost of a module is its interface — that's the complexity it imposes on everyone who uses it. The benefit is its functionality. So the best modules give you a lot of functionality behind a tiny interface. Ousterhout calls these deep. The opposite — a big interface wrapping little functionality — is shallow, and it can be worse than no abstraction at all, because you pay the interface cost without getting much hidden in return.

The classic deep module: Unix file I/O. The interface is five calls — open, read, write, close, lseek — yet it hides buffering, disk scheduling, block allocation, permissions, and device differences. Enormous power, tiny surface. That's depth.

A shallow module looks like this — an interface as complex as the thing it "hides":

// Shallow: the interface tells you everything the body does.
// Pure cost, almost no benefit.
private void addNullValueForAttribute(String attribute) {
    data.put(attribute, null);
}

This is the trap AI tooling pushes you toward. Ask an agent to "refactor for clean code" and you often get more small classes, pass-through wrappers, and one-line helpers — classitis, more interfaces to learn, complexity going up. The code looks tidy and is strictly worse. Catching that is your job, not the model's.

The judgment to internalize For any abstraction, ask: "Is the interface much simpler than what it does for me?" If the interface is about as complex as just doing the work inline, the abstraction hasn't earned its place. Depth, not count, is the measure of good modularity.

Skill · Apply it to your own code (project-driven)

This is where it sticks. You learn best against real work, so:

  1. Open a file you've touched in the last week. Pick one function or class.
  2. Write its interface in one line (name + params + what a caller must know). Now eyeball its body. Is the interface clearly simpler than the body?
  3. Find one shallow module — a wrapper, a pass-through, a class that's basically a struct with getters. Decide: should it be inlined, or deepened by absorbing nearby logic?
  4. Bring it to our next session. We'll use it as the anchor for Lesson 02.
